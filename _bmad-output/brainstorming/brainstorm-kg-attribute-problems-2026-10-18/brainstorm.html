Real or imagined?

Constraint Mapping · data sourcing and engineering; sort real from imagined constraints

Each constraint sorted, then dissolved, routed around or turned into an asset.

  • insight

    Constraint 'raw metadata must be re-downloaded' is mostly imagined for the evaluable catalogue: 94.6% of priced products already have features_text in processed_metadata.csv; only the structured details dict and the category level boundaries truly need the raw file

  • idea

    Quick win, no LLM: store features_text as ParentProduct.features (one SET per product from the CSV) so RS-12 full-text, the Critic and the response generator can read the spec bullets that exist today

  • idea

    Targeted re-download of Amazon Reviews 2023 meta_Electronics (McAuley-Lab, Hugging Face) only to recover the raw details dict, the features list with bullet boundaries, and the categories list, joined by parent_asin to the 161k ingested products; no new products, so the catalogue stays identical

  • insight

    Constraint 'no full-text index on 5.14' is imagined: Neo4j 5.14 community supports CREATE FULLTEXT INDEX with a selectable Lucene analyzer; only the write needs approval later (engineer phase)

  • idea

    Full-text index ft_product_text over title + description + features with an analyzer chosen per catalogue language (Lucene language analyzers stem per language, not per product domain), which satisfies the domain-agnostic rule better than the English unit-stripping in _build_filters

  • idea

    Rebuild the category tree from the 975 distinct categories_text paths: split levels once (word-trie branching points over all paths, checked by one GPT-4o pass over 975 strings, hand-auditable in about an hour), create real SUBCATEGORY_OF edges and a leaf BELONGS_TO_CATEGORY per product

  • insight

    The leaf-category rebuild alone fixes ret_021: the C920's path ends 'Webcams & VoIP Equipment > Webcams', so 'Webcams' resolves to a real leaf instead of failing against main_category 'Computers'; AFP-003's SUBCATEGORY_OF*0..3 traversal finally has a tree to walk (only 33 edges today)

  • idea

    Units are SI/UCUM, not English: parse quantities with a units library (pint or UCUM tables: g, ml, cm, W, mAh, Hz) so the same numeric parser serves cosmetics (50 ml), fashion (cm, g) and electronics; the dimension (mass, volume, power) is the typed key, the surface string is not

  • insight

    Labelling cost is not a real blocker at priced scope: ~62k products x ~600 chars of features is roughly 40M tokens, i.e. tens of dollars on gpt-4o-mini, low hundreds on gpt-4o, zero on a local LLM; the real constraint is audit time, not money

  • idea

    Provenance tiers per fact, recorded as source field + char offsets: details dict (seller-structured) > feature bullet > description > title > review (customer); the tier is shown in explanations ('the listing states', 'reviewers report')

  • idea

    Ghost products: 104k graph products have no metadata (null title, no category); exclude them from candidate generation (p.title IS NOT NULL) and from catalogue denominators, otherwise every coverage statistic (no reviews, no attributes, no category) is diluted

  • question

    Do the 104k ghost products carry reviews? If so the published '53% of products have no reviews' and '81% of priced have no reviews' figures need recomputing on the 161k real products

  • idea

    Coverage-gated hardness: a requested spec becomes a hard Cypher filter only when the attribute is known on at least X% of products in the resolved leaf category; below that it is a soft verify-only signal, which generalises the current MACS demotion into a rule

  • idea

    Additive enrichment: write new facts under new labels/relationships (:Spec or HAS_SPEC with provenance) and leave the legacy Attribute nodes untouched, so R1 runs stay reproducible and 'legacy attributes vs enriched specs' becomes an ablation arm

  • idea

    Graph data version stamp: a (:GraphVersion {attributes:'v2', built:date, source_hash}) node read by evaluate_retrieval.py into manifest.json, so a citable run states which attribute generation it ran on

  • idea

    Test domain-agnosticism at the extraction layer only: pull a small Amazon Reviews 2023 All_Beauty and Amazon_Fashion metadata sample (still the allowed dataset), run the same RS-11 extractor and audit precision there, without ingesting those products into the retrieval graph

  • idea

    The Electronics graph already holds AMAZON FASHION (2,415) and Amazon Home (2,323) products by main_category; use them as an in-graph cross-domain probe for the vocabulary and type matcher

  • fact

    Answered (coach, read-only 2026-10-18): all 104,281 untitled ghost products have reviews and an embedding, none has a price; of 161,026 titled products only 19,439 (12%) have any review; priced: 12,182 of 65,650 (18.6%) as before

  • insight

    The roadmap's '47% of products have reviews' is mostly ghosts: among real (titled) products 88% have no reviews, so P-2 'unknown is the normal case' is even stronger than recorded

  • insight

    Of the 5,715 products with embedded reviews, 4,874 (85%) are ghosts (no title, no price, no category); the review channel mostly finds untitled products, and review-coverage-bias@K's reference set is 85% ghosts

  • idea

    Ghost guard in every channel: candidates must have a title (and a category once rebuilt); unpriced ghosts pass today's 'price IS NULL OR price <= max' filter, so they can enter top-K and silently cost type-precision

  • idea

    Re-run the RS-02 evidence with ghosts excluded: if the review channel's unique finds are ghosts, rrf2 wins by construction and the decision rule should state it

The design space of a fact

Morphological Analysis · data-model design space for RS-11; parameters = fact source, extraction method, vocabulary origin, value type, storage shape, scope, confidence, consumer

Parameters of RS-11 crossed into configurations.

  • idea

    Storage shape: shared key nodes (:FeatureKey {name:'max_resolution', type:'ordinal', dimension}) with the value on the relationship (p)-[:HAS_SPEC {value_num, unit, raw, source, span_start, span_end, extractor, conf}]->(k); values stop being hub nodes, so 'Black' can no longer fan out to 21k products

  • idea

    Hybrid storage: categorical values stay as (:FeatureValue) nodes (useful for graph paths, facets and explanations), numeric and ordinal values live on the HAS_SPEC relationship; IDF per (key, value) comes from a count, not from node degree

  • idea

    Vocabulary induced from the catalogue, not predefined: the LLM extracts free-form key names with spans, keys are embedded and clustered per leaf category, the LLM names each cluster, and an alias table maps raw keys to canonical keys; no hand schema per domain, so it works for fashion or cosmetics

  • idea

    Seed the vocabulary from Amazon's own details keys once the raw metadata is re-downloaded ('Connectivity Technology', 'Item Weight', 'Screen Size' per category); the LLM maps feature prose onto those seller-structured keys, which limits invented key names

  • idea

    Demand-side vocabulary: label only the keys users actually ask about, mined from the tuning-split utterances and gold constraints; smallest labelling job, but must be built from tuning data only to avoid fitting the test split

  • idea

    Set-valued features (compatible_devices = {iPhone 14, iPhone 13}) as a first-class type; they power accessory-for-X detection (RS-09) and the COMPATIBLE_WITH complement edges (RS-14) from the same extraction pass

  • idea

    Range-valued features (operating temperature 0-40 C, strap fits 14-20 cm, 5-12 V input): a request is satisfied on interval overlap or containment, stated per operator

  • idea

    Ordinal ladders stored on the FeatureKey node (720p < 1080p < 1440p < 2160p; S < M < L < XL; SPF 15 < 30 < 50): the LLM proposes the order from observed values, a human confirms per key, so '>= 1080p' is satisfied by 4K

  • idea

    Three extraction states for booleans: stated-present, stated-absent (negated span 'mic not included'), not stated; negation is captured at extraction time with its span, so contradicted means the listing said so

  • idea

    Conflict state when sources disagree (title '4K', features '1080p'): record both with provenance, resolve by source tier, and expose 'disputed' to the verifier so it behaves like unknown rather than confirmed

  • idea

    Variant-aware values at ParentProduct level: 'available in 128/256 GB' becomes a set with a variant flag; a request is satisfiable by some variant, and the explanation says which variant

  • idea

    Confidence by agreement: a fact is confirmed only when two independent extractors agree (regex/unit tier and LLM, or two LLM samples); disagreement downgrades to unknown instead of guessing (P-2 at extraction time)

  • idea

    Mechanical span gate: the quoted span must be an exact substring of the named source field (after whitespace normalisation) and the value must re-parse from the span; deterministic anti-hallucination check, no LLM judge needed, rejection rate reported in the thesis

  • idea

    Spec card: render each product's canonical specs as one short text ('max_resolution: 1080p; microphone: yes, dual') and embed it as one vector per product; the attribute channel then searches spec cards, which removes product-side fan-out by construction

  • idea

    Distillation for the long tail (training relaxed): after LLM labels ~20k products, train a small token-classification tagger (OpenTag/MAVE-style) to label the remaining products cheaply, with the LLM auditing a sample

  • idea

    Extractor choice as an ablation: gpt-4o-mini bulk vs local Qwen/Llama 8B with JSON grammar vs gpt-4o on the 200-product audit set; report precision/recall and cost per 1k products

  • idea

    Scope ladder: (1) priced products in the >= 12 benchmark categories, (2) all priced products (65k), (3) all titled products (161k); stop when the audit shows diminishing returns

Flip the assumption

Assumption Reversal · the code consumers; list each rich-attribute assumption, flip it, rebuild on the flipped version

Every consumer that believed in rich attributes, turned over.

  • assumption

    specs can be hard EXISTS filters

    tap to flip
    reversed

    numeric *_min/_max/_exact never become Cypher filters until coverage exists; only price and brand (real properties/edges) stay hard, and each numeric request is routed to the verifier and logged as verify_only in eval_trace

  • assumption

    the attribute channel finds products

    tap to flip
    reversed

    run rrf without the attribute channel as an arm now (it mostly matches colours), and later make it conditional, running only when the request names a key that is known on enough of the resolved category

  • assumption

    a shared attribute explains

    tap to flip
    reversed

    KECR suppresses any path through a node shared by more than a small share of the category (IDF floor), so 'shares Color: black' (21k products) is never shown; explanation evidence comes from verified spans instead

  • assumption

    the Critic judges fit from vibes

    tap to flip
    reversed

    the batched Critic (RS-17) becomes the interim RS-12 feature check, reading features_text/description of the top 20 and returning per requirement confirmed / contradicted / unknown with a quoted span, passed through the mechanical span gate

  • assumption

    explanations cite attributes

    tap to flip
    reversed

    explanations cite quoted listing text with its source tier ('the listing states: "Built in dual stereo mics"'), and say 'not stated in the listing' for unknown requirements instead of staying silent

  • assumption

    the parser extracts numeric hard constraints

    tap to flip
    reversed

    the parser still extracts typed requirements, but tags them verify_only, and the reply tells the user which requirements were checked against listings and which could not be checked

  • assumption

    users ask for specs

    tap to flip
    reversed

    many requests are use-case level ('for Zoom calls in a dark room'); the LLM turns the use case into feature hypotheses at query time ('low-light correction', 'built-in mic'), which the verifier checks; the raw use case keeps feeding the embedding channel

  • assumption

    unknown is rare

    tap to flip
    reversed

    every retrieval report leads with coverage (share of requested requirements that were checkable at all) before satisfaction, and the UI phrase 'not stated in the listing' becomes a standard response element

  • assumption

    fix the data before evaluating

    tap to flip
    reversed

    make the data gap an experimental condition; arms legacy-attributes vs features-text verifier vs RS-11 specs measure what data enrichment buys, a data-centric ablation that is itself a thesis contribution

  • assumption

    distinguishing features come from attributes' (2026-10-18-014 pt 3)

    tap to flip
    reversed

    a distinguishing feature is a span-verified fact on the target that the same verifier finds stated-absent on peers; peers with unknown values do not count, so the rule stays P-2-safe on empty attributes

  • assumption

    S2 'sparse title needs >= 3 attributes

    tap to flip
    reversed

    require >= 3 span-verified facts from features or description (or a minimum features_text length); otherwise S2 is populated almost only by colour/material/size triples

  • assumption

    S4 'trade-off on known attribute values

    tap to flip
    reversed

    define 'no pool product meets all requirements' on verifier verdicts over listing text, with the target judged best partial match; stratum membership is then reproducible from cached verdicts

  • assumption

    CS@K 'numeric verdicts read numeric_value

    tap to flip
    reversed

    until RS-11 lands, numeric gold constraints are reported as a separate 'not measurable on the live graph' count, not folded into cs_unk where they would hide inside 19-of-19 unknowns

  • assumption

    the benchmark generator reads graph attributes

    tap to flip
    reversed

    the R2b generator reads feature spans (title-blind), so every gold constraint cites its source span on the target; leakage checks must then also cover overlap with the target's features text, not only its title

  • insight

    The interim verifier needs no graph enrichment at all if features_text is stored (one property write) or read from the CSV at query time; the HAS layer can exist in R4 without waiting for RS-11

  • idea

    Eval-time judge for numeric CS@K: a separate extractor (different prompt and ideally different model family than the system's verifier) reads the top-K items' listing text, cached per (asin, constraint); avoids grading the verifier with itself

Future Aenriched + precise

Future A (enriched, precise): coverage-gated hard filters, spec-card attribute channel, contrastive explanations from typed specs; 2026-09-29-007 dynamic domain schemas fall out as a by-product (top keys, units and ladders per leaf category generated from FeatureKey nodes)

Future A query side: the preference parser gets the resolved leaf category's top keys, units and ordinal ladders injected, so requests are labelled into the same vocabulary as products (P-9 closes)

Future Benriched + imprecise

Future B (enriched, imprecise): labels are used only to FIND (recall) and never to filter or confirm; a confirmed state requires a re-read of the quoted span at query time, otherwise the fact counts as unknown

Future Cnot enriched + verifier works

Future C (not enriched, verifier works): query-time LLM verification over listing text of the top 20 is the HAS layer; about 12k input tokens per turn in one batched call, acceptable for a thesis prototype

Future Dneither

Future D (neither): an honest minimal system with the attribute channel off, explanations quoting description text only, and thesis claims scoped to type + embedding + price/brand; this is the floor every plan must still be able to fall back to

  • idea

    Lazy enrichment: every query-time verdict (asin, requirement key, state, span, extractor version) is cached and written back as a provenance-tagged fact, so the KG grows from real demand; offline labelling and query-time checking converge on one store

  • insight

    The move that wins in all four futures is one evidence contract: requirement -> {confirmed, contradicted, unknown, disputed} + quoted span + source tier + extractor id; RS-12 (full-text), the LLM verifier and RS-11 labels are interchangeable providers behind it

  • idea

    EvidenceProvider interface with pluggable backends (fulltext, llm_text_verifier, spec_store); each backend is an evaluation arm, and the Critic, KECR, explanation and CS@K all consume the same verdict objects

  • idea

    Early go/no-go: label a 200-product stratified sample in week one and measure precision and the share of requested keys that are extractable at all; that one number picks the future before the big labelling job starts

  • idea

    Dated fallback rule: if span-gated precision on the audit set is below 0.85 by a set date, RS-11 labels ship as FIND-only (Future B) and the HAS layer stays on the query-time verifier (Future C)

  • idea

    Label confidence feeds the tier rule directly: confirmed needs conf >= tau and a passing span gate; below tau a fact is unknown, so a weak extractor can only lose recall, never create false confirmations

  • question

    Is query-time verification over 20 candidates within the latency budget of the Chainlit UI (p50 642 ms retrieval today), or does it need streaming or precomputation for the top categories?

  • idea

    Precompute verdicts for the benchmark categories only, query-time for the rest; the thesis reports both paths and their agreement on an overlap sample

Borrowed traits

Trait Transfer · other fields that manage messy, partial facts - bioinformatics, Wikidata, libraries, PIM/faceted search, clinical NLP, credit scoring, fact-checking, e-discovery, forecasting

Fields that already live with messy, partial facts.

  • Gene Ontology evidence codes

    every product fact carries an evidence code - STR (seller-structured details), LST (listing text: features/description/title), REV (review-reported), INF (inferred by an LLM from a use case); verifiers and explanations treat codes differently, and the thesis reports facts by code

  • Clinical NLP assertion status

    to product facts: present / absent / possible ('up to 1080p') / conditional ('mic sold separately', 'with adapter') / associated-with-other ('compatible with iPhone 14' describes another device); stops 'iPhone 14' in a case listing being read as the product's own type

  • Thin-file credit scoring

    for products with thin listings, reviews are alternative evidence ('the mic is decent' implies has-microphone, code REV, lower tier); only used to move unknown to weakly-confirmed, never to contradict a listing

  • Forecast calibration

    plot extractor confidence vs audited correctness (reliability diagram, expected calibration error) so the tau in the tier rule is chosen from data, not guessed

  • Recipe ingredient tagging

    (quantity + unit + name, as in the NYT ingredient tagger): the quantity-unit-name triple is language- and domain-neutral and covers '50 ml serum', '65W charger', '32 inch waist'

  • Map shading

    to the UI: the response shows which requirements were checked and which were 'not stated in the listing', so the user sees the evidence map instead of a confident blanket claim

  • idea

    Wikidata-style statements: value + qualifiers (unit, variant, condition) + reference (source field, span) + rank (preferred / normal / deprecated); conflicts resolve by rank instead of overwriting, and nothing is lost

  • idea

    SKOS thesaurus for product types (RS-24): prefLabel, altLabels (synonyms, other languages, plural forms as data not rules), broader/narrower from the rebuilt category tree; matching looks labels up instead of applying English regexes, so fashion and cosmetics need only new label data

  • idea

    GS1-brick idea without GS1 data: attach the expected key set to each leaf product type ('webcam' expects resolution, microphone, mount); 'expected but not stated' is then a recorded, explainable gap rather than silent absence

  • idea

    Faceted-search practice: a key is offered as a filter or facet only when known on >= X% of the current result set (the e-commerce facet-coverage rule), the same rule as coverage-gated hardness, so it is defensible by industry precedent

  • idea

    Clarification by information gain: when results are many, ask about the requirement key with the highest value entropy among candidates that is also known on most of them ('Do you need a built-in microphone?'); ties attribute coverage to Vision §2 Active Clarification

  • idea

    Fact-check card as the explanation unit: claim ('has a built-in mic'), verdict, quoted source, source tier; the response generator may only state claims that have a card

  • idea

    E-discovery split: a stratified random audit sample to estimate label precision honestly, plus a separate uncertainty-sampled set to improve the extractor prompt; never report precision from the uncertainty-sampled set

  • idea

    Spreadsheet type inference per key: a canonical key is typed numeric when >= 80% of its extracted values parse as quantities of one dimension, ordinal when values fall on a small ordered set, categorical otherwise; typing is learned from the data per category

Predators and defences

Predator & Prey · validity threats; name each predator of the enrichment and evaluation plan and evolve a defence

What would eat the plan, and the armour it should grow.

associated-with trap
⟶
an HDMI cable 'compatible with 4K TVs' gets resolution=4K; defence = a 50-item trap set of such listings as a unit test for the extractor, scored before every labelling run
keyword-stuffed compatibility lists
⟶
spans inside long model lists are stored as set-valued associated-with facts, never as the product's own type or features
shared extractor circularity
⟶
if the R2b generator derives gold constraints from the same spans the verifier reads with the same model, CS@K is inflated; defence = gold written by a different model family, human-reviewed, and inter-extractor agreement reported
leak through features
⟶
the title-blind generator still sees model codes inside features text ('C920'); strip alphanumeric model codes and brand tokens from every field shown to the generator, and run the leak check against all generator inputs, not only the title
target privilege
⟶
hand-correcting facts on benchmark targets gives targets cleaner data than their distractors; rule = never hand-edit facts of benchmark products; the audit sample is drawn independently of the benchmark
moving strata
⟶
S2/S4 membership computed from extracted facts changes whenever the extractor changes; freeze stratum membership with the benchmark hash and record the extractor version used to compute it
verbosity returns
⟶
a verifier counting confirmed facts favours long listings (the old verbose-product failure); rank by requested requirements only (confirmed/contradicted/unknown over the request), and report HR by features-text-length quartile to catch it
unit confusion
⟶
reject a value whose unit dimension does not match the key's dimension, and convert within a dimension before comparing
model drift
⟶
gpt-4o aliases change snapshots; pin the dated model ID for labelling, stamp every fact with extractor id + prompt hash, and re-run the 200-item audit after any change
live-graph write risk
⟶
do the enrichment in a separate Neo4j database or after a neo4j-admin dump of the current graph, so R1/R2 runs remain reproducible on the old data
paraphrase overclaim
⟶
the response generator turns 'dual mics' into 'excellent noise-cancelling mic'; a post-generation claim check maps each spec claim in the answer to a fact card (entailment), and unmatched claims are cut or flagged; doubles as the Groundedness metric
electronics smuggling
⟶
a vocabulary built on Electronics hard-codes electronics dimensions; take dimensions and units from UCUM/QUDT tables and keep key discovery data-driven, then test on the Beauty/Fashion sample
eval verifier = system verifier
⟶
CS@K judged by the system's own verifier rewards the system's own mistakes; keep the eval judge separate (prompt, model, cache) and audit a sample by hand
silent coverage shift
⟶
enriched products cluster in some categories, so an arm can win by category mix; report per-category coverage and HR next to every pooled number
  • idea

    Use the OpenAI Batch API for offline labelling (cheaper, no rate-limit pressure) and keep the local LLM as a second opinion on disagreements
